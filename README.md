# React + Vite

This template provides a minimal setup to get React working in Vite with HMR and some ESLint rules.

## Настройка

Backend-переменные окружения задаются в `server/.env` (см. `server/.env.example`).
Обязательные для входа в приложение:

- `APP_PASSWORD` — общий пароль для входа (`POST /api/login`).
- `SESSION_SECRET` — секрет для подписи сессионной cookie (HMAC-SHA256).

Если один из них не задан, пуст, состоит из пробелов или слишком короткий,
сервер отвечает 503 на все `/api/*` запросы (включая логин) и пишет громкую
ошибку в лог при старте — **в любом окружении**, независимо от `NODE_ENV`.
Единственное исключение — локальная разработка: `AUTH_DISABLED=true`
пропускает запросы, но только пришедшие с loopback-адреса. Подробности и
предупреждения — в `server/.env.example`.

## Бэкапы

`server/backup.js` выгружает все четыре коллекции (`transactions`,
`accounts`, `categories`, `settings`) в один EJSON-файл. EJSON, а не обычный
JSON, потому что он сохраняет `ObjectId`, `Date` и числовые типы, а не
превращает их в строки — иначе восстановление дало бы приблизительную копию
документов вместо точной.

```bash
cd server && npm run backup            # в ./backups
cd server && npm run backup -- --out /путь/к/каталогу --keep 30
```

`--keep N` оставляет N последних файлов и удаляет более старые. Ротация
запускается только после того, как новый бэкап успешно записан, поэтому
неудачный запуск не может удалить ничего. Удаляются только файлы, имя
которых в точности совпадает с шаблоном `budget-backup-<дата>.json` — всё
остальное в каталоге скрипт не трогает, потому что каталог может быть
общим (например, синхронизируемая папка облака). Без `--keep` ротации нет.

### Куда складывать: папка облака

Бэкап обязан уезжать с машины, где он сделан. Проще всего — писать сразу в
папку, которую синхронизирует десктопный клиент облака (Яндекс.Диск,
Dropbox, OneDrive): для скрипта это обычный локальный каталог, а выгрузку
берёт на себя клиент.

```bash
# Linux
cd server && npm run backup -- --out ~/Яндекс.Диск/budget-backups --keep 30
# macOS
cd server && npm run backup -- --out ~/Yandex.Disk.localized/budget-backups --keep 30
# Windows (PowerShell)
cd server; npm run backup -- --out "$env:USERPROFILE\YandexDisk\budget-backups" --keep 30
```

Точное имя папки зависит от версии клиента — посмотрите его в настройках
Яндекс.Диска. Каталог создаётся автоматически, если его нет.

Учтите, что файл — это полная финансовая история семьи открытым текстом, и в
облаке она будет лежать в таком же виде.

### По расписанию

Ежедневно в 3:00, Linux/macOS (`crontab -e`):

```cron
0 3 * * * cd /путь/к/budget-tracker/server && /usr/bin/node backup.js --out ~/Яндекс.Диск/budget-backups --keep 30 >> ~/budget-backup.log 2>&1
```

В cron нет вашего обычного окружения, поэтому: полный путь к `node` (узнать
— `which node`), полный путь к каталогу и перенаправление вывода в лог —
иначе об упавшем бэкапе вы узнаете только когда он понадобится. Переменную
`MONGODB_BACKUP_URI` скрипт читает из `server/.env`, так что в crontab её
дублировать не нужно.

На Windows то же самое делается через «Планировщик заданий»: программа —
`node`, аргументы — `backup.js --out ... --keep 30`, рабочая папка —
`...\budget-tracker\server`.

### Проверка доступа

После того как read-only пользователь создан и `MONGODB_BACKUP_URI` прописан
в `server/.env`:

```bash
cd server && npm run backup:check
```

Скрипт подключается, печатает имя базы, читает счётчики и **пробует
записать** — запись должна быть отклонена. Он ловит три ошибки, каждая из
которых иначе проявилась бы позже и молча: строку подключения без имени базы
(подключение уходит в `test`), пустую базу (неверное имя или нет прав) и —
главное — учётку, которая на самом деле умеет писать. Пробная запись идёт в
отдельную коллекцию `__backup_access_check` и удаляется сразу же, так что
реальных данных она не касается даже когда неожиданно проходит.

Скрипт только читает. Задайте `MONGODB_BACKUP_URI` на отдельного
пользователя MongoDB с ролью `read` (рецепт — в `server/.env.example`):
тогда запись запрещает сама база, а не наш код, и credential для бэкапов
отзывается независимо от `APP_PASSWORD`, никого не разлогинивая. Именно этот
путь стоит давать внешнему ассистенту или планировщику.

Если все коллекции оказались пустыми, файл не записывается и скрипт падает с
ненулевым кодом: пустой результат почти всегда означает неверное имя базы в
строке подключения или нехватку прав, и молчаливая запись такого файла
вытеснила бы вчерашний рабочий бэкап.

Восстановление — отдельный CLI-скрипт, а не HTTP-эндпоинт: во всём
приложении нет маршрута, способного перезаписать базу, поэтому ни токен, ни
баг, ни подсунутая ассистенту инструкция не могут запустить restore. Нужен
шелл и креды на запись.

```bash
cd server && npm run restore -- ../backups/budget-backup-….json           # пробный прогон
cd server && npm run restore -- ../backups/budget-backup-….json --yes --replace
```

Без `--yes` скрипт только показывает, что бы он сделал. Непустую базу он
отказывается трогать без `--replace`. Файл проверяется до подключения к
Mongo: неизвестная версия формата или расхождение заявленного и фактического
числа записей (признак обрезанного файла) — отказ.

Каталог `backups/` в `.gitignore`: это полная финансовая история семьи
открытым текстом. Файлы пишутся с правами `0600`. Храните их там, где вы
согласны хранить выписку из банка.

### Проверка файла бэкапа

```bash
cd server && npm run backup:verify -- ~/Яндекс.Диск/budget-backups/budget-backup-….json
```

Не подключается никуда — проверяет сам файл. Сверяет структуру и заявленные
счётчики, ищет документы без `_id` и транзакции, ссылающиеся на счёт,
которого в бэкапе нет, и отдельно ловит потерю типов: даты, приехавшие
строками вместо `Date` (признак того, что файл где-то пересохранили обычным
`JSON.stringify`) — эта поломка иначе не видна до самого восстановления.
Заодно печатает диапазон дат, суммы доходов/расходов и список счетов, чтобы
человек мог узнать свои данные.

Чего эта проверка **не** доказывает: что файл реально ложится обратно в
Mongo. Это доказывает только настоящее восстановление, см. ниже.

### Проверьте восстановление один раз, до того как оно понадобится

На бесплатном тарифе Atlas (M0) нет встроенных снапшотов, поэтому этот
скрипт — единственный бэкап, а непроверенный бэкап бэкапом не является.
Заведите в Atlas второй, пустой кластер или базу, укажите её в `MONGODB_URI`
и прогоните restore на неё. Успешный прогон должен показать те же числа
записей, что и в заголовке файла.

## Дизайн-система

Все значения цвета, кегля и радиуса живут в `:root` в `src/index.css` - это
единственный источник правды. В компонентах сырых значений быть не должно:
только `var(--...)`.

Токен называется по роли, а не по виду: не `--color-red`, а
`--color-negative` (число ушло в минус) и `--color-danger` (удалить, выйти).
Поэтому одно значение может стоять за двумя именами - `--color-border-strong`
и `--color-control-off` сегодня одинаковы, но разъезжаются независимо.

Что уже разложено по токенам:

- **Кегли** - `--text-2xs` (0.7rem) … `--text-3xl` (1.25rem). Крупные
  акцентные числа (сумма на слайде счёта, цифра в кольце лимита) в шкалу не
  входят - они одноразовые и задаются точечно.
- **Радиусы** - `--radius-sm|md|lg|xl` плюс `--radius-pill` для чипов и
  дорожек тумблеров. У вложенного элемента радиус должен быть на ступень
  меньше, чем у родителя, примерно на величину отступа между ними (см.
  `BottomTabs`), иначе внутренний угол выглядит толще внешнего.
- **Цвета** - поверхности (`--color-surface*`), границы (`--color-border*`),
  фирменный, смысловые (`positive` / `expense` / `negative` / `danger` /
  `success` / `warning`), текст.

Пока вне системы (осознанно, до следующего шага):

- **Тени** - шесть разных `boxShadow` заданы по месту; свести их в шкалу
  высот - отдельная задача, там легко испортить глубину.
- **Отступы** - `padding`/`gap` остались числами: их правильнее убирать не в
  токены, а внутрь компонентов-примитивов.
- **Палитра диаграммы** (`COLORS` в `CategoryDonut.jsx`) - это не роли
  интерфейса, а набор различимых между собой цветов для секторов.
- Несколько одиночных оттенков (`#818cf8` у кнопки перевода, `#4ade80`,
  `#94a3b8`) - им нужно решение дизайнера, а не механическая замена.

## Тесты

- `npm test` - модульные тесты (vitest + jsdom).
- `npm run test:e2e` - смоук-тесты в реальном браузере (Playwright + Chromium,
  см. `e2e/`). Нужны для класса багов, которые jsdom в принципе не видит
  (jsdom не делает layout: `offsetWidth`/`offsetLeft`/`getBoundingClientRect`
  всегда 0, `vh` не резолвится, скролл не происходит) - например, карусель
  счетов, съезжающая не туда при свайпе, или шторка операций, оседающая не
  на той высоте. База данных/backend для этого не нужны: Playwright сам
  поднимает dev-сервер Vite, а каждый вызов `/api/**` подменяется фикстурой
  (см. `e2e/fixtures.js`). Перед первым запуском один раз выполните
  `npx playwright install chromium`.

Currently, two official plugins are available:

- [@vitejs/plugin-react](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react) uses [Babel](https://babeljs.io/) (or [oxc](https://oxc.rs) when used in [rolldown-vite](https://vite.dev/guide/rolldown)) for Fast Refresh
- [@vitejs/plugin-react-swc](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react-swc) uses [SWC](https://swc.rs/) for Fast Refresh
