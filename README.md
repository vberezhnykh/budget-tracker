# React + Vite

Актуальный технический аудит и остаточные риски: [AUDIT-2026-09-05](docs/AUDIT-2026-09-05.md).

This template provides a minimal setup to get React working in Vite with HMR and some ESLint rules.

## Настройка

Backend-переменные окружения задаются в `server/.env` (см. `server/.env.example`).
Обязательные для входа в приложение:

- `APP_PASSWORD` — общий пароль для входа (`POST /api/login`).
- `SESSION_SECRET` — секрет для подписи сессионной cookie (HMAC-SHA256).

Для локального запуска backend читает `server/.env`, подключается к MongoDB,
выполняет засев и только после успешного подключения начинает слушать `PORT`
(по умолчанию 5000). Vite проксирует `/api` на `http://localhost:5000`; для
другого адреса задайте только proxy-переменную при запуске Vite, например:
`BUDGET_TRACKER_API_TARGET=http://localhost:5001 npm run dev`. Эта переменная
используется конфигом Vite и не публикуется в клиентский bundle.

Если один из них не задан, пуст, состоит из пробелов или слишком короткий,
сервер отвечает 503 на все `/api/*` запросы (включая логин) и пишет громкую
ошибку в лог при старте — **в любом окружении**, независимо от `NODE_ENV`.
Единственное исключение — локальная разработка: `AUTH_DISABLED=true`
пропускает запросы, но только пришедшие с loopback-адреса. Подробности и
предупреждения — в `server/.env.example`.

### Логотипы расходов через Logo.dev

Для внешних логотипов задайте `VITE_LOGO_DEV_PUBLISHABLE_KEY` в корневом
`.env.local` (образец — [`.env.example`](.env.example)). Используйте только
**publishable key с префиксом `pk_`** из кабинета Logo.dev: он попадает в
клиентскую сборку и запросы картинок. Секретный `sk_` сюда не подходит.
После изменения ключа перезапустите Vite.

В продакшене переменная должна быть доступна **во время `npm run build`**
на хостинге. После её добавления или замены нужна новая сборка; настройка
только в окружении уже запущенного Node-сервера не изменит фронтенд.

Логотипы ищутся по названию операции и загружаются напрямую с
`img.logo.dev`. Пока картинка загружается, если ключ не задан, логотип
не найден или сервис недоступен, видна цветная иконка категории.
Локальный каталог логотипов сохранён в проекте, но его отображение отключено.

В форме добавления и редактирования расхода есть предпросмотр до сохранения.
Кнопка «Выбрать» открывает поиск компаний: название, сайт и логотип помогают
различать одноимённые бренды. Для каталога задайте **серверную** переменную
`LOGO_DEV_SECRET_KEY=sk_…` в `server/.env` и перезапустите сервер. На хостинге
это переменная окружения серверного процесса; её нельзя добавлять в `VITE_*`.
[Brand Search API](https://www.logo.dev/docs/brand-search/introduction)
доступен в том числе на бесплатном тарифе Logo.dev. Ключ остаётся на сервере.

У новых расходов компания и описание разделены: компания — необязательное
название магазина или сервиса, описание — свободный комментарий. Справочник
хранится в MongoDB (`companies`), доступен на всех устройствах через
`GET/POST /api/companies` и `PUT /api/companies/:id`. При сохранении расхода
новая компания добавляется в справочник; совпадения имён без учёта регистра
и лишних пробелов не создают дублей. Изменение выбранной иконки обновляет
настройку компании для следующих покупок.

В операции сохраняются `companyId`, снимок `companyName` и настройки иконки
(`logoMode`, `merchantDomain`). Обновление справочника не меняет эти снимки
у прошлых операций. Для новых покупок без компании используется
`companyName: ''` и иконка категории. Описание не участвует в поиске бренда.

Старые записи без поля `companyName` продолжают показывать прежнее описание
и использовать сохранённый сайт либо прежний автоподбор. Изменение суммы,
даты или категории не добавляет компанию и не сбрасывает иконку. Сама
миграция описаний не идет (разовая чистка запускается вручную, см. «Чистка
старых описаний»): прежние ручные выборы доступны как подсказки
«Из истории» в поле компании и сохраняются в справочник при явном выборе.
Поиск истории и экспорт CSV учитывают компанию и описание отдельно.

Можно ввести сайт вручную, оставить иконку категории (`category`) или
выбрать автоподбор (`auto`) по названию компании.
Запрос к каталогу выполняется только при открытом выборе после паузы ввода
400 мс; предпросмотр также ждёт паузу. При ошибке каталога остаётся ручной
ввод сайта, при ошибке картинки — иконка категории.

Для повторных загрузок используется обычный HTTP-кэш браузера: текущие
[заголовки Logo.dev](https://www.logo.dev/docs/platform/caching) задают
`max-age=86400` (24 часа) и `stale-while-revalidate=600` (10 минут).
Одинаковый URL в пределах срока кэша обычно берётся с устройства, в том
числе после перезагрузки приложения. Браузер может очистить кэш раньше;
после истечения срока потребуется обновление с сервиса. Постоянного
хранилища картинок на нашем сервере или в service worker нет.

### Ввод операции фразой

В форме новой операции над суммой есть строка «Опишите операцию»: фразу вроде
«кофе 3.50 старбакс вчера с карты» разбирает Claude (по умолчанию Haiku 5.5), и
поля формы заполняются черновиком. Ничего не сохраняется само: поля можно
поправить, вернуть кнопкой «Вернуть как было» или сохранить обычной кнопкой.
У правки существующей операции строки нет.

Чтобы включить, задайте **серверную** переменную `ANTHROPIC_API_KEY=…` (ключ из
Anthropic Console) в `server/.env` и перезапустите сервер. На хостинге это
переменная окружения серверного процесса; её нельзя добавлять в `VITE_*`. Без
ключа строка в форме не показывается. Необязательная `QUICK_ENTRY_MODEL`
меняет модель (по умолчанию `claude-haiku-5-5`). Задайте месячный лимит
расходов для ключа в Anthropic Console.

В Claude уходят только фраза, сегодняшняя дата и **названия** категорий,
счетов и компаний (до 500 компаний). Суммы, балансы и история операций не
отправляются. Ответ проверяется на сервере: неизвестные категории и счета,
сумма вне границ и дата дальше года от сегодняшней отбрасываются. Категорию
Claude выбирает по смыслу, а не по точным словам (кроссовки - в одежду, аптека -
в здоровье), и оставляет пустой, только если ни одна не подходит.

Лимиты: 20 разборов в минуту с одного адреса и 300 в сутки на весь сервер
(счётчик в памяти, сбрасывается в полночь по UTC и при перезапуске); ожидание
ответа — 15 секунд. При ошибке, таймауте или исчерпанном лимите поля остаются
доступны для ручного ввода.

**Фото чека.** Кнопка с камерой в той же строке открывает съёмку или галерею;
чек читает Claude Sonnet 5.5 (`claude-sonnet-5-5`), другую модель можно задать
серверной переменной `RECEIPT_MODEL`. Из чека берутся итог, магазин и дата, а
слова в строке («с Revolut») служат пояснением к фото. Если в чеке товары
разных категорий, сумма сразу делится на части через режим разделения; суммы
частей сходятся с итогом, иначе сервер оставляет одну главную категорию. Фото
уменьшается на телефоне (длинная сторона до 2000 пикселей, JPEG) и нигде не
хранится: ни в операции, ни на сервере, ни в service worker; оно живёт в памяти
страницы, пока открыта форма. В Claude уходят само фото, пояснение, сегодняшняя
дата и названия категорий, счетов и компаний. Лимиты: 100 чеков в сутки на
весь сервер (счётчик отдельный от фраз, в памяти) и те же 20 запросов в минуту
с одного адреса; ожидание ответа — 30 секунд.

### Вопросы к данным

На экране «Аналитика» под заголовком есть карточка «Спросить о своих расходах»
(и две подсказки): она открывает чат, где можно спросить словами, например
«сколько ушло на такси за лето против прошлого года» или «на что ушло больше
всего в сентябре». Отвечает Claude Sonnet 5.5 (`claude-sonnet-5-5`), другую
модель можно задать серверной переменной `ASK_MODEL`. Чат - внутренний экран
Аналитики (`#analytics/ask`), из ответа можно открыть Историю с фильтром, по
которому проверяется главное число («Открыть в Истории»).

Модель ничего не считает сама. Она вызывает четыре инструмента поверх тех же
функций, по которым считаются экраны (`server/askTools.js`): `sum_operations`
(итоги и разбивка по месяцам, категориям, компаниям, счетам; можно задать
список из нескольких компаний (до 10), тогда их операции считаются вместе;
переводы и операции «не в статистике» не входят, как и на экранах), `find_operations`
(поиск отдельных операций), `get_balances` (остатки, как на Обзоре) и
`get_typical_month` («обычный месяц»). Числа в ответе берутся из результатов
инструментов; неверный вызов возвращается модели как ошибка, и она может
повторить его. Вид трат («кафе», «такси», «зарплата») модель сопоставляет с
ближайшей категорией и считает через `sum_operations`: текстовый поиск
`find_operations` смотрит только на компанию и заметку, а при пустом результате
в ответе есть подсказка проверить категорию. Если вид трат уже категории
(«такси» в «Транспорте», «бензин» в «Авто», «аптека» в «Здоровье»), модель
сначала группирует категорию по компаниям, выбирает подходящие компании и
отдельным вызовом получает их общую сумму; в ответе называет эти компании, а
итог по всей категории упоминает только как контекст. Инструменты и система уходят с
отдельной точкой кэша промпта, поэтому их префикс переиспользуется и между
разными вопросами (пока те же данные и тот же день).

Итоговый ответ модель отдаёт пятым инструментом `give_answer` (блоки, строка
«что посчитано» и фильтр Истории; схема строгая). Он не считает и не
выполняется: вызов сразу завершает вопрос, другие вызовы из того же хода
отбрасываются, шага в интерфейсе нет. JSON-схема ответа (`output_config.format`)
на раундах с инструментами не отправляется: вместе с `tools` модель не умела
закончить ход текстом и бесконечно вызывала лишние инструменты. Схема уходит
только на последнем запросе после 6 раундов (там инструменты запрещены). Если
модель закончила ход обычным текстом без `give_answer`, он показывается как
текстовый ответ. Тесты сверяют итоги инструментов с `server/analytics.js`,
`server/stats.js` и `server/typicalMonth.js` на одних и тех же данных.

Включается тем же серверным ключом `ANTHROPIC_API_KEY`, что и ввод фразой
(отдельной настройки нет): без ключа карточки на Аналитике нет, а
`POST /api/ask` отвечает 503.

В Claude уходят итоги и найденные инструментом операции (дата, сумма, тип,
категория, название счёта, компания и описание), а также названия категорий и
счетов и вопросы разговора, но не вся история целиком: инструмент отдаёт
не больше 30 операций за вызов. Разговор нигде не хранится: ни на сервере, ни в
`localStorage`; клиент держит его в памяти, пока приложение открыто, и
присылает прошлые реплики текстом с каждым вопросом. «Новый разговор» и выход
из аккаунта очищают его. Ответ идёт потоком: пока Claude считает, на экране
видно, что именно считается.

Лимиты: 10 вопросов в минуту с одного адреса и 100 в сутки на весь сервер
(счётчик в памяти, сбрасывается в полночь по UTC и при перезапуске; считается
только вопрос, дошедший до Claude); не больше 6 раундов с инструментами на
вопрос, после них Claude получает ещё один запрос без инструментов и отвечает
по уже посчитанному (повторный вызов с тем же вводом не выполняется заново),
и 60 секунд на весь ответ; вопрос от 2 до 500 знаков, в разговоре не больше
20 реплик. Если прокси между браузером и сервером копит ответ целиком (nginx
без `X-Accel-Buffering: no`, сжатие), шаги появятся не по ходу, а разом с
ответом; сам ответ при этом приходит.

Если модель отвечает странно (например, повторяет один и тот же вызов), причину
поможет найти серверная переменная `ASK_DEBUG=true` (после смены нужен
перезапуск): в журнал сервера, кроме обычной строки `[ask]`, пишется по строке
`[ask:debug]` на каждый запрос к Claude (что модель вернула, какие вызовы с каким
вводом сделала, что получила в ответ, расход токенов) и форма последнего
запроса (порядок реплик и `tool_use_id` результатов). Эти строки содержат
суммы, категории, ввод инструментов и начало текста модели, поэтому после
разбора переменную нужно снова выключить (убрать или оставить пустой).

### Разбор месяца

Для законченного месяца сервер пишет короткий текст: заголовок и 2-4 пункта о том,
чем месяц отличался от обычного (например, «Сентябрь: на €210 больше обычного из-за
отпуска»). Пишет Claude Sonnet 5.5 (`claude-sonnet-5-5`), другую модель можно задать
серверной переменной `MONTH_REVIEW_MODEL`. На сервере это
`POST /api/month-review` с телом `{ "month": "2026-09", "today": "2026-10-14" }`
(POST, потому что запрос может написать и сохранить разбор).

На «Обзоре» разбор показывает карточка «Итоги сентября»: подпись, заголовок и пункты
сразу под главной карточкой, перед «Счетами». Она видна только в первые 10 дней
месяца (по 10-е число включительно), когда на «Обзоре» выбран текущий месяц, не
выбран никакой счет (разбор про весь бюджет) и в настройках включено `monthReview`.
Приложение просит разбор у сервера один раз за месяц за сеанс и не повторяет запрос
при переключении вкладок; пока он пишется (до нескольких секунд), при ошибке и когда
разбирать нечего (`review: null`), карточки нет, ни заглушки, ни сообщения. Пункт с
категорией - кнопка: она открывает Историю с этой категорией, типом «Расходы» и
разбираемым месяцем. Крестик в углу скрывает карточку; это запоминается на
устройстве (`localStorage`, ключ `monthReview:dismissed:ГГГГ-ММ` для разбираемого
месяца), на другом устройстве карточка появится снова. Если хранилище недоступно,
карточка скрывается до перезагрузки.

Считает код, Claude только выбирает заметное и пишет по-русски
(`server/monthReview.js`). Факты месяца (`buildMonthFacts`) строятся теми же
функциями, что и экраны: расход и доход месяца против «обычного» (медиана за
эталонные месяцы из `server/typicalMonth.js`), отклонения по категориям (до 12, по
убыванию разницы), пять крупнейших операций с пометкой «разовая» (у компании не было
расходов в эталонных месяцах или операция не меньше чем втрое крупнее ее самой
крупной операции за них), месячный лимит (только если месяц его превысил, иначе
в фактах `limit: null` и в тексте его нет) и регулярные платежи. Платеж
регулярный, если в каждом из трех месяцев перед разбираемым у компании 1-2 операции
и месячные суммы в пределах ±5% от их медианы (почти фиксированные платежи: подписки, аренда, связь;
переменные счета вроде электричества не считаются); такой платеж попадает в «изменился»
(сумма отличается от прошлого месяца минимум на 0,50 и на 3%) или в «не прошел».
Месяц не разбирается (`review: null`, `reason: "not_enough_history"`), если он еще не
закончился или полных месяцев истории меньше трех. Операции после месяца факты не
меняют.

В Claude уходят только эти факты: суммы, названия категорий, компании и описания
крупнейших операций и регулярных платежей, но не вся история. Ответ - строгая
JSON-схема (заголовок и пункты с категорией для ссылки в Историю). Если «обычные»
траты категории равны 0, а в части месяцев они были, Claude не пишет «обычно здесь 0»,
а говорит, в скольких из предыдущих месяцев были траты («за полгода до этого траты
здесь были только в одном месяце»). Сервер сверяет
каждое число в тексте с фактами (допустимы числа из фактов, суммы с округлением до
целого евро, числа из дат, малые целые 1-12) и каждую дату словами («14 сентября»,
«1 сентября 2026»): такой день и месяц (с годом, если он указан) должны быть среди
дат фактов, одного совпадения дня недостаточно. Если в тексте есть число или дата вне
фактов, Claude получает один повтор со списком этого; если и после него есть лишнее
или ответ не разобрать, текст не принимается. Подсказка требует, чтобы каждый пункт
был о своей теме: два пункта про одну категорию или одну операцию не пишутся.

Разбор пишется один раз и хранится в коллекции `monthreviews` вместе с хэшем фактов.
Пока факты те же, Claude не вызывается и дневной лимит не тратится. Если факты
изменились (поправили старую операцию), текст пишется заново, но не чаще раза в час:
в этот час отдается прежний с `stale: true`. То же при сбое Claude или исчерпанном
лимите, если прежний текст есть; без него ответ 502 (`MONTH_REVIEW_FAILED`), 504
(`MONTH_REVIEW_TIMEOUT`) или 429. Одновременные запросы на один месяц делят одну
генерацию. Это кэш: коллекцию можно удалить, разбор напишется заново (в бэкап она не
входит).

Включается тем же ключом `ANTHROPIC_API_KEY` (в `features` настроек появилось
`monthReview`), без ключа ответ 503. Лимиты: 20 генераций в сутки на весь сервер
(счетчик в памяти, считается только запрос, дошедший до Claude) и 10 генераций в минуту
с одного адреса; 45 секунд на запрос к Claude. В журнале одна строка
`[month-review] month=… outcome=… attempts=… ms=…` без текстов и сумм.

### Чистка старых описаний

Старая запись - расход без поля `companyName` (у новых оно есть, пустое значит
«без компании»). Ее текст - описание, а если его нет, то `title`. Чистка один раз
просматривает уникальные старые тексты (без учета регистра и лишних пробелов) и для
каждого предлагает один из трех исходов:

- `existing` - это компания из справочника в любом написании («LIDL NICOSIA», «Лидл»,
  «ΣΚΛΑΒΕΝΙΤΗΣ»);
- `new` - конкретная компания, которой в справочнике нет («ИКЕА» - IKEA, «Вольт» - Wolt);
  при применении она добавляется в справочник;
- `note` - не компания: вид трат («Продукты», «Бензин»), место, повод или несколько
  вещей в одном тексте («Продукты, ИКЕА, кофе»). Сомнительное Claude относит сюда.

Тексты, которые совпали с названием из справочника (без учета регистра), находятся без
Claude. Для остальных `server/descriptionCleanup.js` отправляет пачками до 150 текстов
запрос к Messages API через **Batch API** (по умолчанию `claude-sonnet-5-5`, модель
меняет `DESCRIPTION_CLEANUP_MODEL`): чистка разовая, результат не нужен немедленно, а
пакет стоит вдвое дешевле обычных запросов (порядка цента-двух на сотню текстов).
Ответ пакета может прийти через минуты или часы, поэтому прогон хранится в базе
(`DescriptionCleanup`): `POST /api/description-cleanup/start` отправляет пакет,
`GET /api/description-cleanup` при каждом вызове один раз спрашивает его состояние и,
когда пакет закончился, отдает готовые предложения (сначала компании по числу операций,
потом заметки, потом тексты без ответа). Одновременно идет один прогон; запусков не
больше 3 в сутки.

В Claude уходят только тексты, их категории и число операций, а также названия компаний
справочника (до 500). Суммы и даты не отправляются. Ответ проверяется на сервере:
название, которого нет в справочнике, считается новой компанией, непонятные ответы
пропускаются.

`POST /api/description-cleanup/apply` с `{ "keys": [...] }` применяет выбранные
предложения. Для компаний записываются `companyId` и `companyName`, иконка берется из
компании (ручной выбор сайта или категории у операции сохраняется), остаток после
названия («продукты на неделю») становится описанием. Для заметок ставится
`companyName: ''`, а текст остается видимым как описание (для такой записи список
показывает категорию, а описание - комментарием). Операции, которые изменили после
предложения, не трогаются. Перед записью сохраняется копия изменяемых полей: в течение
30 дней `POST /api/description-cleanup/revert` возвращает прежние значения (операции,
которые правили после применения, пропускаются) и удаляет созданные чисткой компании,
на которые больше никто не ссылается. Потом копия стирается.

Включается тем же ключом `ANTHROPIC_API_KEY` (в `features` настроек - `descriptionCleanup`),
без ключа запуск отвечает 503. В журнале одна строка
`[description-cleanup] action=… outcome=… texts=… ms=…` без текстов.

В интерфейсе это «Ещё → Старые описания» (`#more/cleanup`, `CleanupScreen`). Строка
появляется, только если функция включена и есть что делать: остались операции без
компании, идет разбор, список ждет проверки или чистку еще можно отменить. Порядок
такой:

1. «Разобрать» отправляет тексты в Claude. Пакет обрабатывается до часа, приложение
   можно закрыть; экран перечитывает состояние при открытии и при возврате в приложение,
   а кнопка «Проверить» спрашивает сервер сразу.
2. Когда список готов, он разложен по разделам: «Компании» (по одному блоку на компанию,
   у новой пометка «новая», под ней тексты-источники и остаток, который станет
   комментарием), «Останутся описанием» (заметки без компании) и «Без ответа» (их можно
   разобрать позже). Все, что можно выбрать, выбрано сразу; флажки есть у каждого текста,
   у блока компании и у раздела заметок («Выбрать все» / «Снять все»).
3. «Применить к N операциям» после подтверждения отправляет только отмеченные тексты
   (`keys`) и обновляет историю и итоги.
4. Пока не прошло 30 дней, «Отменить чистку до …» возвращает прежние описания (операции,
   которые правили после чистки, не трогаются). Если остались неотмеченные тексты, там же
   можно запустить новый разбор; отмена при этом остается: `GET` отдает ее отдельным полем
   `undo` (применённая чистка, срок которой не вышел), независимо от последнего прогона,
   и экран показывает блок «Прошлая чистка» в любом состоянии.

### Оценка на тестовых данных

`server/eval/` проверяет ввод фразой, вопросы к данным и разбор месяца на настоящем Claude, но
не на настоящих данных: скрипты поднимают MongoDB в памяти (как тесты роутов) и
наполняют ее выдуманной историей за два года (`server/eval/fixtures.js`,
одинаковой при каждом запуске, «сегодня» — 13 октября 2026). Запросы идут через
те же роутеры, что и в приложении. Правильные ответы на вопросы считаются теми
же функциями `server/askTools.js`, и в ответе Claude ищутся эти числа.

```bash
BUDGET_ANTHROPIC_API_KEY=… npm --prefix server run eval:ask    # 22 вопроса, около $0,17
BUDGET_ANTHROPIC_API_KEY=… npm --prefix server run eval:quick  # 15 фраз, меньше цента
BUDGET_ANTHROPIC_API_KEY=… npm --prefix server run eval:month  # 5 месяцев разбора, около 10 центов
BUDGET_ANTHROPIC_API_KEY=… npm --prefix server run eval:cleanup # 58 старых текстов, около 1-2 центов
```

Ключ берется из `BUDGET_ANTHROPIC_API_KEY` (или `ANTHROPIC_API_KEY`) и нигде не
печатается. Аргументы после `--`: `--only id1,id2` (выбранные случаи),
`--repeat N` (каждый случай N раз), `--model <id>`, `--effort <low|medium|high|xhigh|max>`
(уровень размышления вместо заданного в приложении; указывается в отчете),
`--out <папка>` и `--dry` (только посчитать ожидаемые ответы, без запросов к Claude). Отчеты в Markdown и
JSON пишутся в `$EVAL_OUT_DIR` или во временную папку системы (`budget-eval`).
`eval:month` берет месяцы `2026-09,2026-08,2026-05,2026-03,2025-12` (`--only` задает другие),
в базе есть месячный лимит 3500, а сохраненные разборы стираются перед каждым прогоном.
В отчете по месяцу: ключевые факты, текст разбора, число запросов (1 - без повтора),
чужие числа первого ответа, время и стоимость. Обязательно: ответ 200 с разбором, один
запрос без повтора, 2-4 пункта; отмечаются еще заголовок до 80 знаков, название главной
категории отклонения и названия компаний регулярных платежей. С `--dry` печатаются
только факты месяцев.

`eval:cleanup` превращает расходы октября 2024 - января 2025 в старые записи (текст в
`title`, иногда в описании; компании «Парковка» в справочнике нет, там это вид трат) и
сверяет предложения Claude с ожидаемыми для списка из 40 текстов («LIDL NICOSIA», «Вольт»,
«Ужин, машина», «Продукты, ИКЕА, кофе»…). Запросы идут обычным Messages API с теми же
параметрами, что у пакета. Сравниваются вид ответа и название компании без учета
регистра; остаток после названия только печатается. В отчете: точность в целом и по
каждому ожидаемому виду, список расхождений, число точных совпадений без Claude,
стоимость и время. С `--dry` печатаются собранные тексты с ожидаемыми ответами.

В CI и в `npm test` скрипты не входят.

## Загрузка данных на телефоне

Запуск идет одним запросом `GET /api/bootstrap` (те же параметры, что у
сводки): в ответе `{ accounts, categories, settings, dashboard }` - ровно те
данные, что отдают `/api/accounts`, `/api/categories`, `/api/settings` и
`/api/stats/dashboard`. Раньше запуск делал два последовательных захода
(счета, потом остальное). Полная лента Истории запрашивается сразу вслед за
ним, параллельно, а не после. Если сервер еще не знает `/api/bootstrap`
(выкладка идет не мгновенно, ответ 404), приложение один раз загружает данные
по-старому. Остальные чтения итогов (смена месяца и счета, Аналитика) идут в
`/api/stats/dashboard`; первый экран получает итоги с `analytics=0`. Расчеты
всегда учитывают полную историю. Дополнительные
сравнения запрашиваются при открытии вкладки «Аналитика» (`analytics=1`).
Итоги всех месяцев остаются на экране при переключении месяца.

Данные Аналитики для выбранного периода и счета подгружаются в фоне, в
простое браузера, после загрузки Обзора, после смены выбора и после любого
изменения операций (полная перезагрузка сбрасывает кеш итогов и заполняет его
заново). Это тихое чтение: без индикатора обновления и без предупреждения при
ошибке, а вкладка при открытии повторит запрос сама. Поэтому в обычном случае
Аналитика открывается без скелетона.

История загружает весь список под текущий фильтр одним запросом
(`/api/history?continuous=1&all=1`, примерно 60 КБ в сжатом виде на ~2000
операций). Фильтры по счету, категории и типу и поиск `q` применяются на
сервере; разделенная покупка остается одной группой, а сумма дня включает все
подходящие операции. Поиск охватывает всю историю. Последние 8 фильтров
хранятся в памяти телефона: возврат к уже виденному списку мгновенный и без
запроса. Прокрутка и переход к месяцу локальные, без запросов: экран рисует
только окно из ~60 строк и дорисовывает более старые или более новые дни по
мере прокрутки. После изменения операции список перечитывается в фоне; пока
ответ не пришел, на экране остается прежний (с пометкой «Обновление…»), а
позиция прокрутки не сбрасывается. Список другого фильтра, которого еще нет в
памяти, показывается скелетоном. Если обновление не удалось, прежние строки
остаются, а запрос можно повторить. Как и остальные данные, это только память
текущей сессии: при выходе все списки стираются.

Подсказки описаний и прежние варианты компаний запрашиваются при работе с
формой. Экспорт CSV по явному нажатию остается отдельным запросом `/api/transactions`
со всей книгой.
Финансовые данные остаются в памяти текущей сессии, не в кеше PWA.
Сервер по-прежнему рассчитывает сводку по активным операциям в памяти;
эта оптимизация уменьшает передачу данных и вычисления на телефоне.

### Замеры скорости

Сервер и приложение пишут в базу замеры времени (коллекция `perfsamples`):
каждый API-запрос на сервере (путь без query и id, статус, время всего, базы и
расчета), каждый запуск сервера (подключение к базе, засев, время от старта
процесса) и пакеты с телефона (ответ на страницу, время до первых данных,
длительности запросов). Сумм, названий, категорий и текста поиска в них нет.
Записи удаляются сами через 14 дней и в бэкап не входят.

Отчет за последние сутки открывается в браузере под тем же входом:
`/api/perf/report` (параметр `?hours=` до 336). Это обычный текст, его можно
целиком вставить в чат. Запись выключается серверной переменной
`PERF_LOG=off` (после смены нужен перезапуск); отчет при этом читает то, что
уже записано.

### Кэш операций в памяти сервера

Сводка, история, поиск и подсказки раньше при каждом запросе читали из Atlas
все активные операции и счета (около полусекунды на M0) и заново считали
ответ. Теперь сервер держит этот набор в памяти процесса (`server/ledgerCache.js`)
и перечитывает его только после записи. Готовые ответы сводки и истории
запоминаются до следующей записи (`server/responseMemo.js`). Финансовые данные
по-прежнему не сохраняются на телефоне: кэш живёт только в процессе сервера.

- Любая запись в операции или счета (через Mongoose, откуда бы она ни шла)
  сбрасывает кэш и в фоне прогревает его заново, поэтому следующее чтение видит
  запись сразу. Запись внутри транзакции MongoDB сбрасывает кэш ещё раз при
  коммите или откате.
- Запись **не через сервер** (скрипты в `server/*.js`, правка в Atlas) кэш не
  замечает. Снимок старше 10 минут отдается как есть (любого возраста, без
  ожидания Atlas) и в том же запросе обновляется в фоне: первый запрос после
  10 минут запускает обновление, следующий уже видит правку. Если данные в
  Atlas не изменились, версия снимка и готовые ответы сохраняются. Чтобы
  увидеть правку немедленно, перезапустите сервер. Сбой фонового обновления
  пишется в лог вместе с возрастом снимка (устаревший снимок при этом
  продолжает отдаваться).
- Состояние видно в заголовке `Server-Timing` (`cache;desc=hit|miss|stale`), а в
  отчёте `/api/perf/report` (раздел 5) - как доля обращений из памяти по путям.
- Память: порядка нескольких мегабайт на 2-3 тысячи операций плюс до 8 готовых
  ответов истории (до мегабайта каждый).
- `LEDGER_CACHE=off` (после смены нужен перезапуск) выключает кэш целиком:
  каждый запрос читает базу, как раньше. Нужен на случай, если кэш подведёт.

## Обновление установленного приложения

iPhone достаёт приложение с экрана «Домой» из фона вместе со старым кодом, так
что новая сборка раньше появлялась только после закрытия через переключатель
приложений. Теперь, когда приложение снова становится видимым, оно спрашивает
`GET /api/version` (публичный, без кеша; версия - адрес входного модуля из
собранного `dist/index.html`, вроде `/assets/index-C07hSNy2.js`) и сравнивает
с тем, из которого запущено. Проверка идёт не чаще раза в минуту и только
онлайн; ошибки сети молча пропускаются. Если версия сменилась, страница
перезагружается сама.

Та же проверка идет и при запуске. Оболочка приложения (HTML без данных)
отдается service worker'ом из кеша телефона сразу, не дожидаясь сети, а свежая
берется в фоне для следующего запуска; поэтому после выката приложение один раз
открывается на прошлой сборке. Как только данные на экране и браузер свободен,
оно спрашивает версию сервера. Если она новее, приложение просит воркера
принести свежую оболочку в кеш, дожидается ответа и только потом перезагружается
(иначе перезагрузка вернула бы ту же старую оболочку). На каждую версию это
происходит не больше одного раза за сеанс вкладки (в `sessionStorage` лежит
только адрес сборки), так что цикла перезагрузок нет. Данные API в кеш телефона
не попадают никогда.

Когда открыт лист (форма операции, настройки, выбор
периода) или висит тост «Операция в корзине», введённое не теряется: внизу
появляется плашка «Доступна новая версия» с кнопкой «Обновить», а страница
перезагрузится сама, как только листы закроются. В разработке (`npm run dev`)
версии нет, и проверка отключена. После выката владельцу ничего делать не нужно.

## Бэкапы

`server/backup.js` выгружает операции, счета, категории, настройки, планы,
постоянные банковские данные и справочник `companies` в один EJSON-файл.
Текущий формат имеет версию 4; старые файлы версий 1–3 читаются,
а отсутствующие в их формате коллекции нормализуются как пустые.
Связи с компаниями и исторические названия/иконки сохраняются отдельно;
восстановление не заменяет снимки текущими настройками справочника.
EJSON, а не обычный
JSON, потому что он сохраняет `ObjectId`, `Date` и числовые типы, а не
превращает их в строки — иначе восстановление дало бы приблизительную копию
документов вместо точной.

```bash
cd server && npm run backup            # в ./backups
cd server && npm run backup -- --out /путь/к/каталогу --keep 30
```

`--keep N` оставляет N последних файлов и удаляет более старые. Ротация
запускается только после того, как новый бэкап успешно записан, поэтому
неудачный запуск не может удалить ничего. Удаляются только файлы, имя
которых в точности совпадает с шаблоном `budget-backup-<дата>.json` — всё
остальное в каталоге скрипт не трогает, потому что каталог может быть
общим (например, синхронизируемая папка облака). Без `--keep` ротации нет.

### Куда складывать: папка облака

Бэкап обязан уезжать с машины, где он сделан. Проще всего — писать сразу в
папку, которую синхронизирует десктопный клиент облака (Яндекс.Диск,
Dropbox, OneDrive): для скрипта это обычный локальный каталог, а выгрузку
берёт на себя клиент.

```bash
# Linux
cd server && npm run backup -- --out ~/Яндекс.Диск/budget-backups --keep 30
# macOS
cd server && npm run backup -- --out ~/Yandex.Disk.localized/budget-backups --keep 30
# Windows (PowerShell)
cd server; npm run backup -- --out "$env:USERPROFILE\YandexDisk\budget-backups" --keep 30
```

Точное имя папки зависит от версии клиента — посмотрите его в настройках
Яндекс.Диска. Каталог создаётся автоматически, если его нет.

Учтите, что файл — это полная финансовая история семьи открытым текстом, и в
облаке она будет лежать в таком же виде.

### По расписанию

Ежедневно в 3:00, Linux/macOS (`crontab -e`):

```cron
0 3 * * * cd /путь/к/budget-tracker/server && /usr/bin/node backup.js --out ~/Яндекс.Диск/budget-backups --keep 30 >> ~/budget-backup.log 2>&1
```

В cron нет вашего обычного окружения, поэтому: полный путь к `node` (узнать
— `which node`), полный путь к каталогу и перенаправление вывода в лог —
иначе об упавшем бэкапе вы узнаете только когда он понадобится. Переменную
`MONGODB_BACKUP_URI` скрипт читает из `server/.env`, так что в crontab её
дублировать не нужно.

На Windows то же самое делается через «Планировщик заданий»: программа —
`node`, аргументы — `backup.js --out ... --keep 30`, рабочая папка —
`...\budget-tracker\server`.

### Проверка доступа

После того как read-only пользователь создан и `MONGODB_BACKUP_URI` прописан
в `server/.env`:

```bash
cd server && npm run backup:check
```

Скрипт подключается, печатает имя базы, читает счётчики и **пробует
записать** — запись должна быть отклонена. Он ловит три ошибки, каждая из
которых иначе проявилась бы позже и молча: строку подключения без имени базы
(подключение уходит в `test`), пустую базу (неверное имя или нет прав) и —
главное — учётку, которая на самом деле умеет писать. Пробная запись идёт в
отдельную коллекцию `__backup_access_check` и удаляется сразу же, так что
реальных данных она не касается даже когда неожиданно проходит.

Скрипт только читает. Задайте `MONGODB_BACKUP_URI` на отдельного
пользователя MongoDB с ролью `read` (рецепт — в `server/.env.example`):
тогда запись запрещает сама база, а не наш код, и credential для бэкапов
отзывается независимо от `APP_PASSWORD`, никого не разлогинивая. Именно этот
путь стоит давать внешнему ассистенту или планировщику.

Если все коллекции оказались пустыми, файл не записывается и скрипт падает с
ненулевым кодом: пустой результат почти всегда означает неверное имя базы в
строке подключения или нехватку прав, и молчаливая запись такого файла
вытеснила бы вчерашний рабочий бэкап.

Восстановление — отдельный CLI-скрипт, а не HTTP-эндпоинт: во всём
приложении нет маршрута, способного перезаписать базу, поэтому ни токен, ни
баг, ни подсунутая ассистенту инструкция не могут запустить restore. Нужен
шелл и креды на запись.

```bash
cd server && npm run restore -- ../backups/budget-backup-….json           # пробный прогон
cd server && npm run restore -- ../backups/budget-backup-….json --yes --replace
```

Без `--yes` скрипт только показывает, что бы он сделал. Непустую базу он
отказывается трогать без `--replace`. Восстановление пяти коллекций выполняется
одной MongoDB-транзакцией и требует replica set; ошибка поздней вставки
откатывает уже выполненные вставки. Файл проверяется до подключения к Mongo:
неизвестная версия формата, обязательная коллекция или расхождение заявленного
и фактического числа записей (признак обрезанного файла) — отказ.

Каталог `backups/` в `.gitignore`: это полная финансовая история семьи
открытым текстом. Файлы пишутся с правами `0600`. Храните их там, где вы
согласны хранить выписку из банка.

### Проверка файла бэкапа

```bash
cd server && npm run backup:verify -- ~/Яндекс.Диск/budget-backups/budget-backup-….json
```

Не подключается никуда — проверяет сам файл. Сверяет структуру и заявленные
счётчики, ищет документы без `_id`, транзакции и планы, ссылающиеся на счёт
или транзакцию, которых в бэкапе нет, проверяет статусы и связи оплаченных
планов и отдельно ловит потерю типов: даты, приехавшие
строками вместо `Date` (признак того, что файл где-то пересохранили обычным
`JSON.stringify`) — эта поломка иначе не видна до самого восстановления.
Заодно печатает диапазон дат, суммы доходов/расходов и список счетов, чтобы
человек мог узнать свои данные.

Чего эта проверка **не** доказывает: что файл реально ложится обратно в
Mongo. Это доказывает только настоящее восстановление, см. ниже.

### Проверьте восстановление один раз, до того как оно понадобится

На бесплатном тарифе Atlas (M0) нет встроенных снапшотов, поэтому этот
скрипт — единственный бэкап, а непроверенный бэкап бэкапом не является.
Заведите в Atlas второй, пустой кластер или базу, укажите её в `MONGODB_URI`
и прогоните restore на неё. Успешный прогон должен показать те же числа
записей, что и в заголовке файла.

## Интерфейс

Мобильное приложение с нижней навигацией на пять мест: **Обзор**, **История**,
«**+**» (добавить операцию), **Аналитика** и **Ещё**. Макеты и принятые
решения - в [docs/REDESIGN-PLAN.md](docs/REDESIGN-PLAN.md).

- **Экраны** лежат в `src/screens/`: `OverviewScreen`, `HistoryScreen`,
  `AnalyticsScreen`, `MoreScreen`. Внутренние экраны раздела «Ещё» (счета,
  категории, корзина) и листы настроек (правка счёта, лимит месяца) - в
  `src/screens/settings/`. Загрузку данных и состояние держит `App.jsx`, экраны
  получают всё пропсами.
- **Общие детали** - `src/components/ui/`: строка списка, заголовок экрана с
  кнопкой «назад», пустое состояние, встроенное предупреждение, тост, лист
  снизу, кнопки, поля, чипы и другие примитивы (см. «Примитивы» ниже).
- **Токены** (цвета, кегли, отступы, радиусы, тени, шрифт Onest) - в `:root`
  в `src/index.css`.
- **Навигация** живёт в `location.hash` (`src/utils/useHashScreen.js`):
  вкладки - `#history`, `#analytics`, `#more`, Обзор - без хэша; внутренние
  экраны - `#more/accounts`, `#more/categories`, `#more/trash` и
  `#analytics/ask` (вопросы к данным). Переключение
  вкладок не плодит записей в истории браузера, а открытие внутреннего экрана
  добавляет запись, поэтому системный жест «назад» закрывает его, а не уводит
  с вкладки. Обновление страницы возвращает на тот же экран.
- **«Обычный месяц»** считает сервер - `server/typicalMonth.js`: по каждому дню
  месяца медиана накопленного расхода за 6 последних полных месяцев. Из неё
  строятся строка «обычно к этому дню» и прогноз на конец месяца (уже
  потрачено плюс медиана остатков); меньше 3 полных месяцев - прогноза нет.
  Результат приходит полем `typicalMonth` в `/api/stats/dashboard` при
  `timeRange=month`; им пользуются Обзор (плашка последних дней) и график темпа
  на Аналитике.

## Дизайн-система

Все значения цвета, кегля и радиуса живут в `:root` в `src/index.css` - это
единственный источник правды. В компонентах сырых значений быть не должно:
только `var(--...)`.

Токен называется по роли, а не по виду: не `--color-red`, а
`--color-negative` (число ушло в минус) и `--color-danger` (удалить, выйти).
Поэтому одно значение может стоять за двумя именами - `--color-border-strong`
и `--color-control-off` сегодня одинаковы, но разъезжаются независимо.

Что уже разложено по токенам:

- **Кегли** - `--text-2xs` (0.7rem) … `--text-3xl` (1.25rem). Заголовок экрана
  (`--text-title`) и главное число экрана (`--text-display`) в шкалу не входят -
  они существуют в одном экземпляре на экран.
- **Радиусы** - `--radius-sm|md|lg|xl` плюс `--radius-pill` для чипов и
  дорожек тумблеров. У вложенного элемента радиус должен быть на ступень
  меньше, чем у родителя, примерно на величину отступа между ними (см.
  `BottomNav`), иначе внутренний угол выглядит толще внешнего.
- **Цвета** - поверхности (`--color-surface*`), границы (`--color-border*`),
  фирменный, смысловые (`positive` / `negative` / `danger` / `warning`),
  текст.

### Примитивы

`src/components/ui/` - детали, из которых собираются экраны. Правило то же,
что и с токенами: если элемент такого рода уже есть, его берут отсюда, а не
пишут заново инлайновыми стилями.

- **`Field`** - поле ввода. `tone` (на какой поверхности лежит: `outline` /
  `muted` / `sunken`) и `size` (пара «отступы + кегль»). Ширина и место под
  иконку слева остаются на месте вызова - это особенность экрана, а не роль
  поля.
- **`Chip`** - переключаемый выбор. `tone`: `soft` (подсветка - выбор внутри
  формы), `solid` (заливка - включённый фильтр), `quiet` (ячейка периода).
  `shape`: `pill` для чипа с текстом, `block` для плитки. Сам проставляет
  `aria-pressed`.
- **`IconButton`** - кнопка без подписи. `tone` по роли действия (`danger` у
  корзины, `primary` у подтверждения, `neutral` у закрытия, `ghost` внутри
  строки списка), `size` числом, `round` для круглых.
- **`Sheet`** - модальный лист снизу: затемнение, размытие, скруглённые
  верхние углы, отступ под домашний индикатор iOS, появление. Всё
  содержимое - в детях.

- **`Button`** - кнопка с текстовой подписью. `tone` по роли действия
  (`primary`, `secondary`, `soft`, `danger`, `text`), `size` (`sm` / `md` /
  `lg`).
- **`Card`**, **`ListRow`**, **`ScreenHeader`**, **`EmptyState`**,
  **`InlineAlert`**, **`Toast`**, **`SegmentedControl`**, **`Switch`**,
  **`Skeleton`** - карточка, строка списка, заголовок внутреннего экрана,
  пустое состояние, предупреждение в потоке, всплывающее уведомление,
  сегментный переключатель, тумблер и заглушки загрузки.

Шрифт в `Field` намеренно не задаётся: у `<input>` он не наследуется от
`body`, и поля в этом интерфейсе всегда рисовались системным шрифтом.

Пока вне системы (осознанно, до следующего шага):

- **Тени** - частью вынесены в токены (`--shadow-sheet`, `--shadow-toast`,
  `--shadow-menu` и др.), частью заданы по месту. Свести все в шкалу высот -
  отдельная задача, там легко испортить глубину.
- **Отступы** - `padding`/`gap` остались числами там, где элемент не покрыт
  примитивом; внутри `Field`, `Chip`, `IconButton` и `Sheet` они уже
  спрятаны.

## Тесты

- `npm test` - модульные тесты (vitest + jsdom).
- `npm run test:e2e` - смоук-тесты в реальном браузере (Playwright + Chromium,
  см. `e2e/`). Нужны для класса багов, которые jsdom в принципе не видит
  (jsdom не делает layout: `offsetWidth`/`offsetLeft`/`getBoundingClientRect`
  всегда 0, `vh` не резолвится, скролл не происходит) - например, лента
  счетов, которая должна идти одним рядом с горизонтальной прокруткой, или
  экран «История», который обязан занимать высоту окна над нижней панелью. База данных/backend для этого не нужны: Playwright сам
  поднимает dev-сервер Vite, а каждый вызов `/api/**` подменяется фикстурой
  (см. `e2e/fixtures.js`). Перед первым запуском один раз выполните
  `npx playwright install chromium`.
- `npm run lint` - ESLint. Фронтенд разбирается как браузерные ES-модули,
  `server/**` - как CommonJS под Node (см. `eslint.config.js`).

Все три плюс продакшен-сборка гоняются в CI на каждый пуш и пул-реквест
(`.github/workflows/ci.yml`). Серверные тесты используют временную MongoDB
replica set локально и `mongo:7` replica set в CI, а Playwright подменяет
`/api/**` фикстурами. Для запуска приложения есть публичный liveness
`GET /api/health` и readiness `GET /api/ready`, который возвращает 503 до
подключения MongoDB (оба, как и `GET /api/version`, доступны без входа); Vite использует порт 5000 и принимает приватный override
через `BUDGET_TRACKER_API_TARGET`.

Currently, two official plugins are available:

- [@vitejs/plugin-react](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react) uses [Babel](https://babeljs.io/) (or [oxc](https://oxc.rs) when used in [rolldown-vite](https://vite.dev/guide/rolldown)) for Fast Refresh
- [@vitejs/plugin-react-swc](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react-swc) uses [SWC](https://swc.rs/) for Fast Refresh
