## Исправлено

### P1: целостность и валидация backend

- `server/transactionInput.js`: единый `validateTransactionCreate` используется
  для POST и batch; PUT проверяет конечное состояние, включая boolean
  `excludeFromStats` и разные source/destination для transfer.
- `server/app.js`: удаление группы split проверяет найденный transaction и его
  принадлежность запрошенному `splitId`; GET transactions использует `.lean()`.
- `server/auth.js`: режим `AUTH_DISABLED` проверяет и socket `remoteAddress`, и
  `req.ip`; внешний запрос не получает локальный bypass.

### P1/P2: клиентские состояния и доступность

- `src/utils/finance.js:getPeriodData`: split без description больше не падает;
  `src/components/AddTransactionForm.jsx` сохраняет значения форм при ошибках
  POST/PUT/DELETE, повторная отправка блокируется во время pending.
- `src/App.jsx` и `src/components/AccountsSettingsModal.jsx`: pending-состояния
  account/limit форм и обработка ошибок мутаций сохранены; после accounts
  загрузка transactions/categories/settings выполняется через `Promise.all`.
- `src/components/ui/Sheet.jsx`: focus trap, Tab/Shift+Tab, Escape и возврат
  фокуса после закрытия покрыты тестом.

### P1: CI, зависимости и git hygiene

- `package.json`: postinstall теперь запускает `npm --prefix server ci`, поэтому
  server ставится по lockfile, а не через недетерминированный `npm install`.
- `.github/workflows/ci.yml`: cache setup-node теперь учитывает оба lockfile;
  Mongo service для checks и Chromium с кешем для e2e существовали до этой правки.
- `.gitignore`: защищены `server/.env.backup`,
  `server/backup_before_multiaccounts/` и `server/**/*.xlsx`; `.env.example`
  не попадает под правило.
- Root lockfile обновлён в пределах существующих диапазонов: Vite 7.3.0 → 7.3.6,
  Rollup 4.63.1, PostCSS 8.5.28, Picomatch 4.0.7, Babel 7.29.7.

### PWA (проверено, без изменений)

## Остаточные риски

### P1

- `src/App.jsx` (`fetchAccounts`, `fetchTransactions`): сетевые исключения в
  `fetchTransactions` оставляют пустые значения/нули. Нужны явные error/retry
  состояния и время последней синхронизации.
- `server/app.js` (`PUT /api/categories/:id`): переименование категории сначала сохраняет Category,
  затем делает `Transaction.updateMany`; сбой между операциями оставляет частичное
  переименование. Нужна Mongo session transaction на replica set либо миграция
  на `categoryId`, с тестами отказа.
- `server/app.js` (`PUT /api/transactions/:id`): concurrent PUT выполняет read-current → validate →
  update без OCC; два patch могут нарушить совместный invariant. Нужна проверка
  версии/условие обновления и тест гонки.

### P2

- `server/app.js` (`PUT /api/settings`, `Settings.findOneAndUpdate({})`) не гарантирует singleton;
  параллельная первая запись может создать два документа. Нужны уникальный ключ,
  контролируемая миграция и защита от concurrent write race.
- `server/app.js` (`/api/stats/*`, `GET /api/search`, `GET /api/suggestions/descriptions`): stats/search/suggestions читают полную коллекцию;
  клиент также держит всю историю и пересчитывает фильтры. Pagination отложена
  решением владельца до измерения мобильного профиля.
- `vite.config.js` (`server.proxy['/api']`) проксирует на 5001, `server/index.js` (`PORT`) по умолчанию
  слушает 5000; root `start` загружает `.env` из cwd, тогда как README описывает
  `server/.env`. Нужен единый контракт запуска.
- `server/app.js` (`GET /api/transactions`): сортировка только по `date` делает страницы нестабильными
  при одинаковых датах. При внедрении pagination нужны cursor `date+_id` и
  compound index.
- `src/App.jsx` (`handleAddCategory`) / `AddTransactionForm.jsx` (`handleCreateCategory`): UI создания
  категории не показывает `result.error` пользователю.
- `server/app.js`: остаётся добавить внешнее monitoring-покрытие для liveness,
  readiness и локального structured error log.
- `server/app.js` (`app.set('trust proxy', 1)`): `trust proxy=1` корректен только при ровно одном доверенном
  reverse proxy; при другой топологии rate limit может получить неверный `req.ip`.

### Зависимости

Повторный root `npm audit --omit=dev` показывает 0 уязвимостей после обновления
lockfile. Server сохраняет 3 пакета уровня moderate в одной цепочке зависимостей:
`express@4.22.2` → `body-parser@1.20.6` → `qs@6.15.3`. Целевые обновления в
текущих диапазонах изменений не дали; `qs` 6.16.0 не совместим с диапазоном
`~6.15.1`. Это одна цепочка, а не три независимых дефекта. Исходники не вызывают
`qs.stringify`, и эксплуатация advisory в приложении не доказана. Исправление
требует отдельного совместимого override/обновления цепочки с тестами.

Vite обновлён до 7.3.6 по [официальному advisory Vite](https://github.com/vitejs/vite/security/advisories/GHSA-fx2h-pf6j-xcff).
Риск относится к dev server и требует сетевого доступа к нему; утечка production
не подтверждена. Для qs см. [primary advisory qs](https://github.com/ljharb/qs/security/advisories/GHSA-4mjr-xmp4-gh2g).

Стандартный `npm run lint` всё ещё находит 2 `no-unused-vars` в нетронутом
пользовательском untracked `server/create_backup.js` (`docsDev`/`docsProd`).
Файл не запускался и не менялся; lint tracked JS/JSX и новый `Sheet.test`
проходит.

## Предложения и порядок

1. Reliability: error/retry при начальной загрузке, readiness Mongo и monitoring.
2. Integrity: атомарные category rename и restore, singleton Settings.
3. Функции: лимиты категорий и CSV import preview с duplicate detection.
   Undo/корзина и предстоящие разовые платежи уже реализованы; регулярные
   операции отклонены в текущем плане, экспорт уже есть.
4. Performance: сначала измерить мобильный профиль, затем pagination и переход
   клиента на серверные агрегаты.

Для каждой P1 правки нужны тест отказа/повторной попытки и критерий: пользователь
видит ошибку и может повторить действие, а частичное финансовое состояние не
становится успешным. Для pagination критерий — стабильный порядок и одинаковый
итог дня при разбиении списка.

comparison+series+categoryComparison+monthlyTotals`: 1,000 операций — 3 ms /

мобильный UX и не доказывает эффект будущей pagination.

338.02 kB / 102.71 kB gzip. Это небольшое увеличение размера, а не улучшение
производительности.
